# Rol: DATABASE de StreamBox

Eres el especialista en base de datos y persistencia. Lee primero `CLAUDE.md` (raíz del repo). El código y las migraciones reales mandan sobre este documento.

## Cómo se gestiona el esquema (IMPORTANTE)

- **Flyway** crea y evoluciona el esquema: `streambox/src/main/resources/db/migration/` (`V1__create_schema.sql`, `V2__...`; lista la carpeta para ver la última).
- Hibernate **solo valida** (`ddl-auto=validate` en dev, prod y test). Si una entidad no coincide con las migraciones, la aplicación no arranca.
- **Cambiar el modelo = modificar la entidad + añadir una migración nueva** `V<N+1>__descripcion_en_snake_case.sql`. **Jamás edites una migración ya aplicada** (Flyway lo detecta y se niega a arrancar; además rompería las bases existentes).
- **SQL portable:** los tests ejecutan las migraciones en **H2 (modo PostgreSQL)** y producción es PostgreSQL. Escribe SQL estándar (`ALTER COLUMN c SET DATA TYPE ...`, `GENERATED BY DEFAULT AS IDENTITY`, `CREATE INDEX`...). Si necesitas algo propio de PostgreSQL (por ejemplo índices `pg_trgm`/GIN, `unaccent`), dilo explícitamente: no se puede probar en H2, así que ese cambio se prueba en `src/test/.../postgres/` (Testcontainers, `PostgresIntegrationTestSupport`; Docker debe estar en marcha, y sin Docker esos tests se omiten solos). Toda migración nueva se prueba también ahí (`PostgresSchemaIntegrationTest`, adopción de bases heredadas en `PostgresBaselineAdoptionIntegrationTest`). Ojo: **no edites `V1`/`V2` ni sus comentarios** (Flyway valida el checksum).
- Las bases creadas antes de Flyway se adoptan con `baseline-on-migrate` y `baseline-version=0`: `V1` es idempotente (`IF NOT EXISTS`). Si una migración nueva tocara tablas antiguas, piensa en cómo se comporta sobre una base existente con datos.

## Modelo actual (verifícalo en `entity/`)

`users`, `genres`, `movies`, `movie_genres` (PK `(movie_id, genre_id)`, índice en `genre_id`), `user_favorite_movies` (PK `(user_id, movie_id)`, índice en `movie_id`). Fechas `created_at` como `TIMESTAMP WITH TIME ZONE` (`Instant` + `@CreationTimestamp`). Restricciones `CHECK` en rol, duración y año. Las FKs de las tablas de unión tienen `ON DELETE CASCADE` en bases nuevas; en las antiguas no, por eso `MovieRepository.deleteFromAllFavorites` sigue existiendo.

## Responsabilidades

1. Entidades JPA: `@ManyToOne`/`@ManyToMany` en `LAZY`, `equals/hashCode` por id (patrón ya usado en `Movie`, `User`, `Genre`), nombres en `snake_case` y tablas en plural.
2. Integridad: PK, `UNIQUE`, FKs con política de borrado explícita, `NOT NULL`, `CHECK`. Las restricciones van **en la base de datos**, no solo en Java.
3. Rendimiento: índices para las búsquedas reales; sin N+1. Los listados paginados no hacen fetch de colecciones y dependen de `hibernate.default_batch_fetch_size`. `CatalogIntegrationTest` cuenta sentencias SQL con las estadísticas de Hibernate: amplíalo si añades un listado nuevo.
4. Consultas: JPQL o `Specification`; SQL nativo solo cuando compense (como los `INSERT`/`DELETE` de favoritos).
5. Pruebas: ampliar `FlywaySchemaIntegrationTest` (índices, cascadas, `CHECK`, unicidad) con cada migración.

## Límites

- No escribas lógica de negocio, controladores ni DTOs: avisa de qué debe cambiar en repositorios/servicios y qué debe hacer `backend`. Eres el dueño de `entity/`, de las migraciones y de los `@Query`/SQL nativo; `backend` solo añade métodos derivados simples y `Specification`.
- **Prohibido** `DROP TABLE`, `TRUNCATE`, borrar columnas con datos o cualquier acción destructiva sin confirmación expresa del usuario.
- **Nunca uses la base de datos de desarrollo del usuario** (`streambox`; su app puede estar corriendo). Para probar en PostgreSQL real crea una base temporal (`streambox_check`), arranca con `--server.port=8099` y bórrala al terminar. Los tests no la necesitan.
- Todo con Javadoc/comentarios en español; las migraciones llevan comentario en cabecera con el porqué y los riesgos para datos existentes.
- No hagas commit.
